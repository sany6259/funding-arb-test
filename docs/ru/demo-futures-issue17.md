# Bybit и OKX: фьючерсный демопуть (Issue #17)

**NO-GO для торгового запуска.** Этот Draft PR добавляет изолированные
приватные маршруты Bybit Demo и OKX Demo, но полное исполнение пары в рабочем
приложении ещё не разрешено. Текущая веб-панель и существующий CLI не запускают
этот модуль, а `execute_pair` намеренно отклоняет запрос на этапе `_preflight`.
Существующие блокировки production и Bybit Testnet не ослаблены.

Транспорт допускает только Bybit `https://api-demo.bybit.com` и OKX
`https://www.okx.com` с заголовком `x-simulated-trading: 1` на каждом приватном
запросе. Для него используются только данные отдельных демосчетов из `age`;
переадресации и повторная отправка запроса на создание ордера запрещены.
Нужны одновременно режим `demo`, явное разрешение процесса
`FARB_ENABLE_DEMO_ORDERS=1` и подтверждение вызывающего кода; `FARB_DRY_RUN=1`,
`FARB_LIVE=1`, `DCA_LIVE=1` и Bybit Testnet блокируют отправку. Этот процессный
флаг не является включением ордеров в веб-панели и не заменяет отдельного
разрешения владельца. Другие способы вызова внутренних функций не являются
поддерживаемым интерфейсом.

Каркас предназначен только для двух **фьючерсных** ног: Bybit linear perpetual
и OKX USDT swap. Количество OKX указывается в контрактах; до запуска необходимо
получить и проверить размер контракта и шаги инструмента на бирже. Тесты подменяют
незавершённый preflight и всю сеть: подтверждённый полный fill первой ноги
необходим до отправки второй. `New`, частичное исполнение, неизвестный ответ,
таймаут и ошибка требуют ручной сверки и не вызывают автоматического отката.
Журнал намерения записывается до отправки, блокировка исключает параллельный
запуск; оставшийся журнал запрещает повтор до ручной сверки. Даже два полных
fill возвращают `position_reconciliation_required`, а не успех стратегии.

Для Issue #19 добавлены **только офлайн** проверка нормализованных снимков и
проверка согласованности предоставленных сведений об ордерах, исполнениях и
позициях. Проверка количества учитывает общий шаг Bybit и размер/шаг контракта
OKX; проверяются давность данных, funding и время выплат, спред, режим счёта,
маржа, плечо, комиссии, проскальзывание и явно переданные лимиты. Результат
расчёта не доказывает происхождение снимков из demo API и не является допуском
к сделке. При подтверждении владельца модуль может построить **офлайн-план**
двух противоположных `reduce-only` закрытий по полностью согласованным данным;
он не подписывает и не отправляет эти ордера. Частичные и неизвестные исходы
остаются на ручной сверке и не дают создать такой план.

Перед практическим демо требуется реализовать и проверить preflight по обеим
биржам: доверенные demo-only сборщики данных, интеграцию их с офлайн-проверкой,
проверку рисков текущей стратегии и подтверждение фактических ответов бирж.
Также нужны сверка после каждого шага и перезапуска, защищённое закрытие и
подтверждение остатков обеих ног, привязка к pure-futures исполнителю, проверка
режима и разрешения между процессами, подготовка age-хранилища на VPS и
отдельная проверка владельца.
Реальные API-ответы, точные права демоключей и работа VPS в этом PR не проверены.
Неизвестный ключ по его строке нельзя надёжно классифицировать как production
или demo; вводите только ключи, созданные в демосредах.

После отдельного разрешения на установку кода на VPS команда **только локальной
offline-диагностики**, без обращения к биржам и без ордеров:

```sh
cd /opt/funding-arb-test
FARB_DRY_RUN=1 .venv/bin/python scripts/cli/demo_futures_readiness.py
```

Ожидается `NOT READY` и код выхода `2`. Команды для фактической отправки демоордеров
в этой версии нет; не обходите блокировку `_preflight`. См. также инструкцию
[предварительной проверки VPS](vps-pr16-preflight.md). Базовый PR #16 остаётся
незамерженным, поэтому этот PR создан поверх его ветки.

Для безопасного локального просмотра **состояния** существующего журнала после
перезапуска можно добавить `--journal` к той же команде. Вывод содержит только
состояние, названия бирж и наличие подтверждённых идентификаторов, без ключей;
код `2` и `NOT READY` сохраняются. Повреждённый или занятый журнал считается
неопределённым. Команда не обращается к биржам, не стирает журнал и не
разрешает повторный вход.

При `reconciliation_required`, таймауте, `New` или частичном исполнении
остановите автоматизацию и сохраните журнал. После отдельного разрешения
владельца проверьте обе ноги, заявки и исполнения в интерфейсах именно
демосчетов, сопоставив идентификаторы с защищённым локальным журналом. Не
передавайте ключи или содержимое журнала в чат. Не удаляйте журнал и не
повторяйте заявки, пока состояние обеих бирж и необходимых закрытий не будет
однозначно установлено. При обнаружении прежней реальной позиции используйте
утверждённый владельцем ручной порядок непосредственно на соответствующей бирже;
эта версия бота не выполняет аварийное закрытие.
